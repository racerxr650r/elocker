# elocker (`elc`)

`elc` provides an accurate calculation of your application's effective lines of code (ELOC) and so much more. It analyzes your source code to
measure its scale, quality, and architecture. Instead of relying on guesswork or pattern matching, `elc` parses the code directly to generate
per-function metrics and whole-project analysis for C, C++, Rust, and Python. It presents this information in tabular and graphic forms with
a variety of output formats.

`elc` really shines when you provide an elf filename generated from the provided source files. The tool will prune functions and conditionally
compiled lines of source that aren't in the generated binary before performing analysis and generating the metrics. If the elf contains debug
information, the tool can parse additional information to allow it to expand the code using the gcc pre-compiler for applicable languages. If
you are analyzing a library that was linked with the application code, just provide the source files/directories of the library along with the
elf file. The tool will prune those source and analyze the appropriate sources, ignoring the rest of the binary.

In this day ans age of AI generated code, `elc` is an excellent way to keep your finger on the pulse of your source project as AI contributes.

## What it does

Point `elc` at a file, directory, or Git repository to generate a detailed report.

*   **Project Summary:** Overview of the project provided. Information provided includes; Number of files, Physical lines, ELOC, Number of functions, Critical findings count, and Warning findings count.
*   **Findings:** See [Every finding elc can report](https://github.com/racerxr650r/elocker/blob/develop/README.md#every-finding-elc-can-report) below.
*   **File-Level Metrics:** Overview of the source files included in the project.
*   **Function-Level Metrics:** Identifies where your complexity lives. Reports include function name, source file, line number, language, visibility, complexity, fan-in, fan-out, and maintainability index.
*   **System Architecture:** Maps how your project fits together. By combining per-file syntax trees into a single System Dependence Graph, `elc` identifies dependency cycles, architectural bottlenecks, call stack depths, and unreachable code.
*   **Build-Specific Analysis:** Analyzes the code you actually ship. Pass a configuration (`-D`) or a linked image (`--elf`), and `elc` evaluates the compiled program rather than the raw source. This reveals which `#ifdef` branches were actually taken, locates functions generated by macros, and prunes uncalled functions eliminated by the linker.

## Why another metrics tool

Most metrics tools analyze code per file and per language. In polyglot repositories, this forces you to juggle multiple incompatible tools. `elc` takes a different approach:

| Feature | Why it matters |
| :--- | :--- |
| **Per function, not per file** | A 2,000-line file doesn't tell you which of its 40 functions is causing problems. |
| **Parses, never guesses** | Metrics come from a true syntax tree. It correctly handles complex nested comments where regex-based counters fail. |
| **Universal definitions** | ELOC and complexity are calculated consistently across all languages, making metrics directly comparable. |
| **Deterministic output** | Identical input produces byte-identical output. Results can be reliably diffed and tracked across versions. |
| **Architecture, not just size** | Identifies dead code via graph reachability, catching issues textual linters miss (e.g., unused functions that call each other). |
| **Measures, never lectures** | Findings map to published standards (MISRA C, Martin's Instability, Henry–Kafura). `elc` provides data, not style opinions. |
| **Small and self-contained** | A single C11 binary. No interpreters, VMs, networks, plugins, or servers required. |

## Every finding elc can report

`elc` reports 15 kinds of findings. Each names the measurement,
the subject it was taken from, and **the authority it is judged against** — so a
published rule and one of `elc`'s own judgements can never be mistaken for each
other.

### Banded — the value decides the severity

Nothing is reported for a healthy figure.

| Measurement | Per | Warning | Critical | Source |
| --- | --- | --- | --- | --- |
| `fan-out` | function | above 10 | above 15 | Henry-Kafura |
| `complexity` | function | above 10 | above 15 | McCabe (NIST SP 500-235) |
| `fan-in` | function | above 25 | *(none)* | elc heuristic |
| `weighted test burden` | function | 20 or above | 45 or above | elc heuristic |
| `call depth` | project | above 8 | above 12 | embedded practice (PVD A.2) |

`fan-in` has no critical band deliberately: no published source divides fan-in
into accepted and unaccepted ranges, so 25 is already a judgement and a second
line would be a second unsupported claim.

### Occurrence — the fact itself is the finding

There is no acceptable number of these, so there is nothing to band.

| Measurement | Per | Severity | Fires when | Source |
| --- | --- | --- | --- | --- |
| `recursion` | cycle | critical | a call cycle exists | MISRA C Rule 17.2 |
| `component dependency cycle` | cycle | critical | files depend on each other | Martin, acyclic dependencies |
| `shared state` | global | critical | reached from the application *and* from an interrupt handler, without `volatile` | C11 §6.7.3, §7.14.1.1 |
| `shared state` | global | warning | reached from the application *and* from a registered callback whose thread `elc` cannot place | C11 §6.7.3, §7.14.1.1 |
| `critical section` | function | critical | re-entrant, and a path leaves it holding a lock it acquired | elc heuristic |
| `critical section` | function | info | re-entrant, and its control flow could not be built — *not analysed*, never *safe* | elc heuristic |
| `single-function global` | global | warning | one function names it; it belongs at block scope | MISRA C Rule 8.9 |
| `hidden channel` | global | warning | shared across call-graph regions that never call each other | MISRA C Rule 8.9 |
| `confined qualifier` | global | warning | `volatile` and reached from one thread of control only | elc heuristic |
| `instability` | component | warning | its measured instability contradicts the layer you declared it in | Martin |
| `bottleneck` | component | warning | Ca and Ce both at or above the threshold (default 5, `-b`) | elc heuristic |
| `misra library` | call site | warning | a call to a C library function MISRA C:2012 §21 forbids | MISRA C:2012 |

### What needs `elc` needs declared

Four findings cannot be reported unless you provide `elc` information it cannot
infer:

| Finding | Needs |
| --- | --- |
| `call depth` | `--entry` |
| `instability` | `--stratum` |
| `shared state`, `confined qualifier`, `critical section` | an interrupt handler `elc` can identify — a macro-written definition, `--isr-regex`, or `--elf` |

### `elc heuristic` means exactly what it says

Six of the fifteen are `elc`'s own judgement rather than a published rule, and
every one of them is labelled **`elc heuristic — not a published standard`** in
the `Source` column.

No finding severity ever reaches the exit status. `elc` reports; what to do
about it is yours.


## What `elc` output looks like

Reports render as an aligned table to stdout (default), CSV, XML, HTML, or GitHub-Flavored
Markdown, with a Graphviz `.dot` call tree written with the same filename. 

The XML form is acomplete record of a run, so a report can be regenerated later against a
different complexity threshold without re-analysing the source.

The HTML form can be opened in a browser. It presents a graphical dynamic call graph that can be
expanded or collapsed at the file level. This makes browsing larger projects much more managable.

The Markdown form presents a number of tables applicable to the analysis. These tables are in a
drop-down format. They are closed when the document is opened to make navigating to the table of
interest much easier.

## Theory of Operation

`elc` reads each source file and generates an Abstract Syntax Tree (AST). 
A file's extension selects a grammar. No language,
file extension, or grammar node type is compiled into the binary. Prior to parsing, the file
is expanded by the project's local preprocessor(s) where one is available and measured as
written where it is not. Everything then comes out of the resulting AST:
effective lines, cyclomatic complexity, visibility, call sites, global accesses,
critical sections, and the rest are all *queries against the parse*. The per-file facts are
resolved against one another into one project-wide **System Dependence Graph**,
and every whole-project question — coupling, dependency cycles, call depth,
reachability, the second thread of control — is determined from that graph rather than
the source. Then a separate stage compares the figures against
published thresholds and turns them into findings. And, finally a renderer
converts the internal dependency graph into a **Call Graph** (CFG). Measurement, judgement,
and presentation are three stages generating a table, Markdown, CSV,
XML, or an interactive HTML graph.
